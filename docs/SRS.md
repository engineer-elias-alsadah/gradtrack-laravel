# وثيقة متطلبات البرمجيات المصغرة (Mini-SRS)
## مشروع منصة GradTrack لإدارة وتتبع مشاريع التخرج والهندسة البرمجية
### Graduation Project & Milestone Management Portal

---

* **المقرر:** هندسة البرمجيات - العملي (Software Engineering Lab)
* **العام الجامعي:** 2026 / 2027
* **إشراف المهندس:** ساهر الهمداني
* **إعداد الطالب:** إلياس جمال الساده
* **الإصدار:** 1.0.0
* **الحالة:** معتمدة ومكتملة للتنفيذ (Approved for Implementation)

## 1. وصف المشكلة (Problem Description)

في البيئة الأكاديمية ومشاريع التخرج الهندسية، تواجه الفرق الطلابية والمشرفون الأكاديميون عدة تحديات جوهرية:
1. **غياب المتابعة المرحلية (Lack of Milestone Tracking):** يُترك تسليم المشاريع حتى نهاية الفصل الدراسي دون تقسيم مراحل العمل (Milestones)، مما يسبب تراكم الأعباء وتسليمات غير مكتملة أو رديئة الجودة.
2. **تشتت قنوات التواصل والملاحظات:** ضياع ملاحظات المشرف وتعديلاته المطلوبة بين رسائل البريد الإلكتروني، وتطبيقات المراسلة الفورية، والأوراق المطبوعة، مما يُصعّب تتبع سجل التغييرات والوفاء بمتطلبات التعديل (Revisions).
3. **غياب الشفافية في التقييم:** صعوبة معرفة الطالب لمستوى تقدمه الفعلي، ودرجات كل مرحلة، والمواعيد النهائية (Deadlines) بدقة.
4. **عدم مطابقة المنهجيات الهندسية:** عدم تطبيق ممارسات هندسة البرمجيات مثل دورات المراجعة (Peer Review)، معايير القبول، وتتبع حالات الفشل والحدود (Edge Cases).

---

## 2. الحل المقترح (Proposed Solution)

تطوير منصة ويب متكاملة **(GradTrack)** مبنية على إطار العمل **Laravel**، تُمكّن الطلاب والمشرفين من تنظيم مشاريع التخرج وفق أفضل ممارسات هندسة البرمجيات (Agile / Milestone-driven Development):
* تقسيم كل مشروع تخرج إلى مراحل محددة (Milestones) بأوزان نسبية ومواعيد نهائية واضحة.
* إتاحة بوابة رفع التسليمات (Submissions) تشمل التقارير، روابط مستودعات GitHub، والملاحظات.
* نظام مراجعة وتقييم للمشرف يقدم تغذية راجعة فورية (Feedback)، وقرارات واضحة: (معتمد / يحتاج تعديل / مرفوض).
* لوحة تحكم إحصائية للطلاب والمشرف توضح نسبة الإنجاز، المهام المتبقية، والتقييمات التراكمية.

## 3. المستخدمون المستهدفون (User Personas)

| المستخدم (Persona) | الدور والمسؤوليات | الاحتياج الأساسي |
| :--- | :--- | :--- |
| **الطالب (Student / Team Lead)** | قائد أو عضو فريق المشروع (مثل: الطالب إلياس الساده). | استعراض المراحل، رفع ملفات وروابط التسليم قبل الموعد النهائي، وتتبع الملاحظات والدرجات. |
| **المشرف الأكاديمي (Supervisor)** | مهندس أو دكتور المادة (مثل: المهندس ساهر الهمداني). | جدولة المراحل، مراجعة التسليمات، تقديم تغذية راجعة تفصيلية، واعتماد أو طلب تعديل التسليم. |
| **منسق القسم / المدير (Admin / Coordinator)** | رئيس القسم أو منسق مشاريع التخرج. | نظرة شمولية على جميع المشاريع، نسب الإنجاز العامة، واستخراج تقارير الأداء. |

## 4. نطاق المشروع (Project Scope)

### 4.1 داخل النطاق (In-Scope):
* تسجيل الدخول بنظام الأدوار والصلاحيات (Role-Based Access Control: Student, Supervisor, Admin).
* إنشاء المشاريع وربطها بالمشرف والطلاب.
* إدارة مراحل المشروع (Milestones): العنوان، الوصف، الموعد النهائي، الوزن المئوي، والحالة.
* دورة تسليم المراحل (Submission Workflow): ملاحظات، ملف، رابط مستودع GitHub، ورقم الإصدار.
* دورة المراجعة والتقييم (Review & Grading): التغذية الراجعة، قرار الاعتماد، والدرجة المستحقة.
* لوحة معلومات (Dashboard) تعرض نسب الإنجاز والتنبيهات.
* سجل العمليات والتغييرات (Activity Audit Log).

### 4.2 خارج النطاق (Out-of-Scope - للإصدارات المستقبلية):
* بوابات الدفع الإلكتروني (غير مطلوبة أكاديمياً).
* محادثات الفيديو المباشرة داخل المنصة (يتم استخدام منصات الجامعة المعتمدة).
* التصحيح التلقائي للأكواد البرمجية بالذكاء الاصطناعي (سيتم كإضافة في v2.0).

## 5. المتطلبات الوظيفية (Functional Requirements - FR)

* **FR-01 (إدارة الحسابات):** يجب أن يتيح النظام تسجيل الدخول، والتحقق من صلاحية المستخدم بناءً على دوره (Student / Supervisor / Admin).
* **FR-02 (إدارة المشاريع):** يجب أن يتمكن المشرف/المنسق من إنشاء مشروع وربطه بالطلاب وتعيين المشرف المسؤول.
* **FR-03 (جدولة المراحل - Milestones):** يجب أن يتمكن المشرف من إضافة مراحل للمشروع مع تحديد تاريخ الاستحقاق ونسبة الدرجة.
* **FR-04 (رفع التسليمات - Submissions):** يجب أن يتمكن الطالب المصرح له فقط من تسليم المرحلة برفع ملاحظات ورابط GitHub وملف مرفق.
* **FR-05 (المراجعة والتقييم - Reviews):** يجب أن يتمكن المشرف من تقييم التسليم، كتابة ملاحظات دقيقة، واختيار حالة التسليم (Approved / Needs Revision / Rejected).
* **FR-06 (تعديل التسليمات):** إذا كانت الحالة (Needs Revision)، يجب أن يتاح للطالب رفع إصدار جديد (Version 2) مع الحفاظ على سجل الملاحظات السابقة.
* **FR-07 (حساب نسب الإنجاز):** يجب أن يقوم النظام بحساب النسبة المئوية لإنجاز المشروع تلقائياً بناءً على المراحل المعتمدة.

---

## 6. المتطلبات غير الوظيفية (Non-Functional Requirements - NFR)

* **NFR-01 (الأداء - Performance):** يجب ألا يتجاوز زمن استجابة صفحات النظام 1.5 ثانية في ظل الاستخدام العادي.
* **NFR-02 (الأمان - Security):**
  * تشفير كلمات المرور باستخدام خوارزمية `Bcrypt`.
  * حماية المسارات (Route Protection) بواسطة Laravel Middleware والـ Policies.
  * الحماية ضد هجمات CSRF, XSS, و SQL Injection عبر الـ Eloquent ORM و Blade Engine.
* **NFR-03 (سهولة الاستخدام - Usability):** واجهة مستخدم نظيفة ومتجاوبة (Responsive) تدعم الشاشات المكتبية والهواتف، مع دعم كامل للغة العربية (RTL).
* **NFR-04 (الموثوقية وقابلية الصيانة - Maintainability & Reliability):**
  * بنية معمارية قياسية وفق نمط MVC في Laravel.
  * تغطية برمجية باختبارات آلية (Feature & Unit Tests) لا تقل عن 80% للعمليات الحساسة.
  * تشغيل الاختبارات تلقائياً عبر GitHub Actions CI عند كل Push أو Pull Request.

## 7. قصص المستخدمين مع معايير القبول (User Stories & Acceptance Criteria)

### 📖 قصة المستخدم 1: رفع تسليم مرحلة المشروع (Student Submission)
* **الصياغة:** بصفتي **طالباً وقائد مشروع**، أريد **رفع تسليم مرحلة معينة متضمناً رابط مستودع GitHub والملاحظات**، حتى **أتمكن من توثيق عمل الفريق وإرساله للمشرف للمراجعة قبل الموعد النهائي**.
* **معايير القبول (Given / When / Then):**
  * **سيناريو 1 (التسليم الناجح):**
    * **Given:** الطالب مسجل الدخول، وهو عضو في هذا المشروع، والمرحلة مفتوحة وحالتها (Pending أو Needs Revision).
    * **When:** يقوم الطالب بملء حقل الملاحظات، وإدخال رابط GitHub صالح، والضغط على "إرسال التسليم".
    * **Then:** يتم حفظ التسليم في قاعدة البيانات، وتتحول حالة المرحلة إلى `Submitted`، وتظهر رسالة تأكيد خضراء.
  * **سيناريو 2 (بيانات غير صالحة):**
    * **Given:** الطالب في صفحة التسليم.
    * **When:** يترك حقل الملاحظات فارغاً أو يُدخل رابطاً غير صالح لمستودع GitHub.
    * **Then:** تظهر رسائل خطأ واضحة باللون الأحمر لكل حقل، ولا يتم إنشاء أي سجل جديد.

---

### 📖 قصة المستخدم 2: تقييم المشرف وتقديم الملاحظات (Supervisor Review)
* **الصياغة:** بصفتي **مشرفاً أكاديمياً**، أريد **مراجعة تسليم الطلاب وإعطاء درجة وتغذية راجعة وتحديد القرار**، حتى **يعرف الطلاب مواطن القوة والضعف ويعدلوا المطلوب إن لزم**.
* **معايير القبول (Given / When / Then):**
  * **سيناريو 1 (اعتماد التسليم بنجاح):**
    * **Given:** المشرف مسجل الدخول، وهو المشرف المعين لهذا المشروع، والمرحلة تم تسليمها (`Submitted`).
    * **When:** يُدخل المشرف الدرجة (مثلاً 95/100) ويكتب ملاحظات المراجعة ويختار الحالة `Approved` ثم يضغط "حفظ التقييم".
    * **Then:** يتم حفظ المراجعة، وتتحول حالة المرحلة إلى `Approved`، وتُحدث نسبة إنجاز المشروع العامة فورياً.
  * **سيناريو 2 (طلب إعادة تعديل):**
    * **Given:** التسليم يحتوي على نواقص برمجية.
    * **When:** يختار المشرف `Needs Revision` مع تدوين الملاحظات.
    * **Then:** تتغير حالة المرحلة إلى `Needs Revision` ويُسمح للطالب برفع إصدار جديد للتسليم.

---

### 📖 قصة المستخدم 3: حماية الصلاحيات والخصوصية (Authorization & Isolation)
* **الصياغة:** بصفتي **طالباً في المشروع**، أريد **أن تقتصر صلاحية تسليم وتعديل المراحل على أعضاء فريقي فقط**، حتى **لا يتمكن أي طالب من فريق آخر من العبث بمشروعنا**.
* **معايير القبول (Given / When / Then):**
  * **سيناريو 1 (محاولة وصول غير مصرح):**
    * **Given:** طالب مسجل دخوله ولكنه لا ينتمي للمشروع رقم (1).
    * **When:** يحاول إرسال طلب POST لتسليم مرحلة في المشروع رقم (1) أو استعراض صفحة التسليم الخاصة به.
    * **Then:** يقوم النظام برفض الطلب وإرجاع رمز الاستجابة `403 Forbidden` برسالة واضحة "غير مصرح لك بالوصول لهذا المشروع".

## 8. مصفوفة حالات الحافة (Edge Cases Matrix)

وفقاً لما تم التأكيد عليه في المحاضرة الأولى (شريحة 10): "المسار الطبيعي لا يكفي، مهندس البرمجيات يفكر فيما قد يحدث عند الفشل أيضاً":

| التصنيف | حالة الحافة (Edge Case) | سيناريو الفشل المحتمل | المعالجة الهندسية في النظام (Handled Solution) |
| :--- | :--- | :--- | :--- |
| **البيانات (Data)** | إرسال حقول فارغة أو مسافات فقط | انهيار الاستعلام أو إدخال بيانات مشوهة | استخدام `FormRequest` في لارافيل بقواعد: `required\|string\|min:10` مع `trim` تلقائي. |
| **البيانات (Data)** | رابط GitHub غير صحيح (مثل نص عادي) | تعطل رابط المشروع عند فتحه من قبل المشرف | تطبيق Validation Rule: `url\|regex:/^https:\/\/github\.com\/.+/i`. |
| **البيانات (Data)** | نصوص وملاحظات طويلة جداً | تجاوز سعة حقول التخزين في قاعدة البيانات | تقييد الحقل بـ `max:5000` واستخدام عمود `TEXT` في قاعدة البيانات. |
| **الصلاحيات (Auth)** | طالب يحاول تقييم نفسه كأنه المشرف | تلاعب بالدرجات والنتائج الأكاديمية | حماية الإجراء عبر `Gate::authorize('review-submission')` و Laravel Policy. |
| **الصلاحيات (Auth)** | محاولة تعديل تسليم معتمد ومغلق | العبث بمخرجات تم تقييمها سابقاً | التحقق من شرط `milestone->status !== 'approved'` قبل قبول أي تسليم جديد. |
| **الوقت والتاريخ (Time)** | تسليم بعد انتهاء الموعد النهائي (Deadline) | خلاف بين الطالب والمشرف حول وقت التسليم | يقبل النظام التسليم ولكن يُسجل كـ `Late Submission` مع توثيق وقت التأخير بالساعات. |
| **الوقت والتاريخ (Time)** | إنشاء مرحلة بتاريخ ماضي | اضطراب الجدولة الزمنية | تطبيق قاعدة التحقق `date\|after_or_equal:today` عند إضافة أي موعد مرحلة جديدة. |
| **الشبكة والنظام (System)** | الضغط المتكرر السريع على زر التسليم (Double Click) | إنشاء تسليمين متطابقين في نفس اللحظة (Race Condition) | تعطيل الزر برمجياً عبر الـ JS فور الضغط، مع فحص وجود تسليم معلق عبر قفل قاعدة البيانات (Database Transaction). |
| **الشبكة والنظام (System)** | انقطاع الجلسة (Session Expiration) أثناء كتابة تقرير طويل | ضياع الملاحظات بعد الضغط على إرسال | حفظ مسودة الملاحظات محلياً (LocalStorage) وإعادة توجيه واضحة لتسجيل الدخول دون فقد المسودة. |

## 9. خطة الاختبار وضمان الجودة (Quality Assurance & Testing)

1. **Unit Testing:** اختبار الدوال المساعدة مثل حساب النسبة المئوية لإنجاز المشروع، والتحقق من حساب الأوزان.
2. **Feature Testing:**
   * اختبار مسار تسجيل الدخول (`AuthTest`).
   * اختبار حماية المسارات ورفض غير المصرح لهم (`AuthorizationTest`).
   * اختبار عمليات رفع التسليم وتقييم المشرف (`MilestoneSubmissionTest`).
   * اختبار حالات الحافة لمنع التسليم المزدوج والبيانات غير الصالحة (`EdgeCasesTest`).
3. **التكامل المستمر (CI):** تشغيل كافة الاختبارات تلقائياً عبر GitHub Actions قبل السماح بدمج أي فرع في `main`.
