## 1. المشاكل الخمس الأساسية (The 5 Core Problems)

في البيئة الأكاديمية ومشاريع التخرج الهندسية، تواجه الفرق الطلابية والمشرفون الأكاديميون خمس مشاكل جوهرية:
1. **المشكلة الأولى: غياب المتابعة والجدولة المرحلية (Lack of Milestone Tracking):** يُترك تسليم المشاريع حتى نهاية الفصل الدراسي دون تجزئة زمنية لمراحل العمل (Milestones)، مما يسبب تراكم الأعباء وتسليمات غير مكتملة أو رديئة الجودة.
2. **المشكلة الثانية: تشتت قنوات التواصل وضياع الملاحظات (Feedback Dispersal):** ضياع ملاحظات وتوجيهات المشرف وتعديلاته المطلوبة بين رسائل البريد الإلكتروني، وتطبيقات المراسلة الفورية، والأوراق المطبوعة، مما يُصعّب تتبع سجل التغييرات والوفاء بمتطلبات التعديل (Revisions).
3. **المشكلة الثالثة: عشوائية إدارة الأكواد وانعدام الربط بـ GitHub (Unstructured Code Versioning):** عدم ربط المخرجات بمستودعات برمجية رسمية وفروع واضحة (Git Flow)، مما يُفقد المشروع قيمته الهندسية ويصعب التحقق من مساهمات الطلاب.
4. **المشكلة الرابعة: ضعف الأمان وتداخل الصلاحيات (Authorization & Security Gaps):** غياب عزل البيانات بين الفرق الطلابية، ومحاولة الطلاب تقييم أنفسهم أو التعديل على مشاريع الفرق الأخرى دون قيود صلاحيات صارمة.
5. **المشكلة الخامسة: إهمال حالات الفشل والحدود وغياب الاختبارات (Neglecting Edge Cases & CI/CD):** عدم التفكير المسبق في السيناريوهات الشاذة (كالنقر المزدوج السريع، الروابط المشوهة، وتجاوز المواعيد)، وغياب الاختبارات الآلية المؤتمتة لفحص النظام قبل النشر.

## 2. الحلول الهندسية الخمسة المقترحة (The 5 Proposed Engineering Solutions)

تطوير منصة ويب متكاملة **(GradTrack)** مبنية على إطار العمل **Laravel**، تقدم خمسة حلول هندسية مباشرة ومطابقة للمشاكل:
1. **حل المشكلة 1 (جدولة المراحل):** تقسيم كل مشروع تخرج إلى مراحل محددة (Milestones) بأوزان نسبية ومواعيد نهائية واضحة، مع احتساب آلي لنسب التقدم التراكمية.
2. **حل المشكلة 2 (بوابة مراجعة تفاعلية):** نظام مراجعة وتقييم للمشرف يقدم تغذية راجعة فورية (Feedback)، وقرارات واضحة: (معتمد / يحتاج تعديل / مرفوض)، مع دعم أرقام الإصدارات المتعددة (v1, v2).
3. **حل المشكلة 3 (تكامل Git & GitHub):** إلزامية إرفاق روابط مستودعات وفروع GitHub مع كل تسليم، وتطبيق سير العمل عبر فروع الميزات وطلبات الدمج (Pull Requests).
4. **حل المشكلة 4 (حوكمة الصلاحيات RBAC):** حماية أمنية مشددة عبر سياسات Laravel Policies و FormRequests تمنع أي طالب من الوصول لمشروع فريق آخر (403 Forbidden) وتمنع التقييم الذاتي.
5. **حل المشكلة 5 (معمل حالات الحافة والتكامل المستمر CI/CD):** معالجة شاملة لـ 9 حالات حافة، وتفعيل خط أنابيب GitHub Actions CI لتشغيل 19 اختباراً آلياً بـ PHPUnit تلقائياً عند كل Push أو PR.

## 3. المستخدمون المستهدفون (User Personas)

| المستخدم (Persona) | الدور والمسؤوليات في النظام | الاحتياج الأساسي |
| :--- | :--- | :--- |
| **الطالب (Student)** | طالب أو قائد فريق مشروع تخرج (مثل الطالب: إلياس جمال الساده، أو أي طالب مسجل جديد). | استعراض متطلبات المراحل، رفع ملفات وروابط مخرجات GitHub قبل الموعد النهائي، وتتبع الملاحظات والدرجات. |
| **المشرف الأكاديمي (Supervisor)** | مهندس أو دكتور المادة (مثل المهندس: ساهر الهمداني، أو أي مشرف أكاديمي مسجل جديد). | إنشاء مشاريع التخرج وتعيين قادة الفرق، جدولة المراحل وأوزانها، مراجعة التسليمات، تقديم التغذية الراجعة، واعتماد أو طلب تعديل التسليم. |

## 4. نطاق المشروع (Project Scope)

### 4.1 داخل النطاق (In-Scope):
* تسجيل حساب جديد وتسجيل الدخول بنظام الأدوار والصلاحيات (Role-Based Access Control: Student, Supervisor).
* تمكين المشرف من تأسيس مشاريع التخرج، وتعيين قادة وأعضاء الفرق الطلابية.
* جدولة مراحل المشروع (Milestones): العنوان، الوصف، الموعد النهائي، الوزن المئوي، والحالة.
* دورة تسليم المراحل (Submission Workflow): ملاحظات تفصيلية، ملف مرفق، رابط مستودع GitHub، ورقم الإصدار.
* دورة المراجعة والتقييم (Review & Grading): التغذية الراجعة، قرار الاعتماد، والدرجة المستحقة (0 - 100).
* لوحة تحكم ذكية (Dashboard) تعرض نسب الإنجاز التراكمية والتنبيهات.
* معمل حالات الحافة التفاعلي (Interactive Edge Cases Lab) لتوضيح الحماية البرمجية.
* سجل العمليات والتغييرات (Activity Audit Log).
* أتمتة الاختبارات والتكامل المستمر (GitHub Actions CI/CD).

### 4.2 خارج النطاق (Out-of-Scope - للإصدارات المستقبلية):
* بوابات الدفع الإلكتروني (غير مطلوبة أكاديمياً).
* محادثات الفيديو المباشرة داخل المنصة (يتم استخدام منصات الجامعة المعتمدة).
* التصحيح التلقائي للأكواد البرمجية بالذكاء الاصطناعي (سيتم كإضافة في v2.0).

## 5. المتطلبات الوظيفية (Functional Requirements - FR)

* **FR-01 (إدارة الحسابات):** يجب أن يتيح النظام إنشاء حساب جديد وتسجيل الدخول، وتحديد الصلاحيات بناءً على دور المستخدم (Student / Supervisor).
* **FR-02 (تأسيس المشاريع):** يجب أن يتمكن المشرف الأكاديمي من إنشاء مشروع تخرج جديد وتحديد بياناته وتعيين قائد الفريق من الطلاب المسجلين.
* **FR-03 (إدارة أعضاء الفريق):** يجب أن يتمكن المشرف من إضافة أعضاء من الطلاب المسجلين إلى فريق عمل المشروع.
* **FR-04 (جدولة المراحل - Milestones):** يجب أن يتمكن المشرف من إضافة مراحل للمشروع مع تحديد تاريخ الاستحقاق ونسبة الدرجة.
* **FR-05 (رفع التسليمات - Submissions):** يجب أن يتمكن الطالب المصرح له فقط من تسليم المرحلة برفع ملاحظات ورابط GitHub وملف مرفق.
* **FR-06 (المراجعة والتقييم - Reviews):** يجب أن يتمكن المشرف المعين للمشروع من تقييم التسليم، كتابة ملاحظات دقيقة، واختيار حالة التسليم (Approved / Needs Revision / Rejected).
* **FR-07 (تعدد الإصدارات Revisions):** إذا كانت الحالة (Needs Revision)، يجب أن يتاح للطالب رفع إصدار جديد (Version 2) مع الحفاظ على سجل الملاحظات السابقة.
* **FR-08 (حساب نسب الإنجاز):** يجب أن يقوم النظام بحساب النسبة المئوية لإنجاز المشروع تلقائياً بناءً على المراحل المعتمدة.

## 6. المتطلبات غير الوظيفية (Non-Functional Requirements - NFR)

* **NFR-01 (الأداء - Performance):** زمن استجابة صفحات النظام أقل من ثانية واحدة تحت الضغط الاعتيادي.
* **NFR-02 (الأمان - Security):**
  * تشفير كلمات المرور باستخدام خوارزمية `Bcrypt`.
  * حماية المسارات (Route Protection) بواسطة Laravel Middleware والـ Policies.
  * الحماية ضد هجمات CSRF, XSS, و SQL Injection عبر الـ Eloquent ORM و Blade Engine.
* **NFR-03 (سهولة الاستخدام - Usability):** واجهة مستخدم نظيفة ومتجاوبة (Responsive) تدعم الشاشات المكتبية والهواتف، مع دعم كامل للغة العربية (RTL).
* **NFR-04 (الموثوقية وقابلية الصيانة - Maintainability & Reliability):**
  * بنية معمارية قياسية وفق نمط MVC في Laravel.
  * تغطية برمجية باختبارات آلية (Feature & Unit Tests) تغطي كافة المسارات وحالات الحافة.
  * تشغيل الاختبارات تلقائياً عبر GitHub Actions CI قبل السماح بدمج أي فرع في `main`.

## 7. قصص المستخدمين مع معايير القبول (User Stories & Acceptance Criteria)

### 📖 قصة المستخدم 1: رفع تسليم مرحلة المشروع (Student Submission)
* **الصياغة:** بصفتي **طالباً وقائد مشروع**، أريد **رفع تسليم مرحلة معينة متضمناً رابط مستودع GitHub والملاحظات**، حتى **أتمكن من توثيق عمل الفريق وإرساله للمشرف للمراجعة قبل الموعد النهائي**.
* **معايير القبول (Given / When / Then):**
  * **سيناريو 1 (التسليم الناجح):**
    * **Given:** الطالب مسجل الدخول، وهو عضو في هذا المشروع، والمرحلة مفتوحة وحالتها (Pending أو Needs Revision).
    * **When:** يقوم الطالب بملء حقل الملاحظات، وإدخال رابط GitHub صالح، والضغط على "إرسال التسليم".
    * **Then:** يتم حفظ التسليم في قاعدة البيانات، وتتحول حالة المرحلة إلى `Submitted`، وتظهر رسالة تأكيد خضراء.
  * **سيناريو 2 (بيانات غير صالحة):**
    * **Given:** الطالب في صفحة التسليم.
    * **When:** يترك حقل الملاحظات فارغاً أو يُدخل رابطاً غير صالح لمستودع GitHub.
    * **Then:** تظهر رسائل خطأ واضحة باللون الأحمر لكل حقل، ولا يتم إنشاء أي سجل جديد.

---

### 📖 قصة المستخدم 2: تقييم المشرف وتقديم الملاحظات (Supervisor Review)
* **الصياغة:** بصفتي **مشرفاً أكاديمياً**، أريد **مراجعة تسليم الطلاب وإعطاء درجة وتغذية راجعة وتحديد القرار**، حتى **يعرف الطلاب مواطن القوة والضعف ويعدلوا المطلوب إن لزم**.
* **معايير القبول (Given / When / Then):**
  * **سيناريو 1 (اعتماد التسليم بنجاح):**
    * **Given:** المشرف مسجل الدخول، وهو المشرف المعين لهذا المشروع، والمرحلة تم تسليمها (`Submitted`).
    * **When:** يُدخل المشرف الدرجة (مثلاً 95/100) ويكتب ملاحظات المراجعة ويختار الحالة `Approved` ثم يضغط "حفظ التقييم".
    * **Then:** يتم حفظ المراجعة، وتتحول حالة المرحلة إلى `Approved`، وتُحدث نسبة إنجاز المشروع العامة فورياً.
  * **سيناريو 2 (طلب إعادة تعديل):**
    * **Given:** التسليم يحتوي على نواقص برمجية.
    * **When:** يختار المشرف `Needs Revision` مع تدوين الملاحظات.
    * **Then:** تتغير حالة المرحلة إلى `Needs Revision` ويُسمح للطالب برفع إصدار جديد للتسليم.

---

### 📖 قصة المستخدم 3: حماية الصلاحيات والخصوصية (Authorization & Isolation)
* **الصياغة:** بصفتي **طالباً في المشروع**، أريد **أن تقتصر صلاحية تسليم وتعديل المراحل على أعضاء فريقي فقط**، حتى **لا يتمكن أي طالب من فريق آخر من العبث بمشروعنا**.
* **معايير القبول (Given / When / Then):**
  * **سيناريو 1 (محاولة وصول غير مصرح):**
    * **Given:** طالب مسجل دخوله ولكنه لا ينتمي لهذا المشروع.
    * **When:** يحاول إرسال طلب POST لتسليم مرحلة في هذا المشروع أو استعراض صفحة التسليم الخاصة به.
    * **Then:** يقوم النظام برفض الطلب وإرجاع رمز الاستجابة `403 Forbidden` برسالة واضحة "غير مصرح لك بالوصول لهذا المشروع".

## 8. مصفوفة حالات الحافة (Edge Cases Matrix)

وفقاً لما تم التأكيد عليه في المحاضرة الأولى (شريحة 10): "المسار الطبيعي لا يكفي، مهندس البرمجيات يفكر فيما قد يحدث عند الفشل أيضاً":

| التصنيف | حالة الحافة (Edge Case) | سيناريو الفشل المحتمل | المعالجة الهندسية في النظام (Handled Solution) |
| :--- | :--- | :--- | :--- |
| **البيانات (Data)** | إرسال حقول فارغة أو مسافات فقط | انهيار الاستعلام أو إدخال بيانات مشوهة | استخدام `FormRequest` في لارافيل بقواعد: `required\|string\|min:10` مع `trim` تلقائي. |
| **البيانات (Data)** | رابط GitHub غير صحيح (مثل نص عادي) | تعطل رابط المشروع عند فتحه من قبل المشرف | تطبيق Validation Rule: `url\|regex:/^https:\/\/github\.com\/.+/i`. |
| **البيانات (Data)** | نصوص وملاحظات طويلة جداً | تجاوز سعة حقول التخزين في قاعدة البيانات | تقييد الحقل بـ `max:5000` واستخدام عمود `TEXT` في قاعدة البيانات. |
| **الصلاحيات (Auth)** | طالب يحاول تقييم نفسه كأنه المشرف | تلاعب بالدرجات والنتائج الأكاديمية | حماية الإجراء عبر دالة `authorize()` وفحص دور المستخدم `isSupervisor()`. |
| **الصلاحيات (Auth)** | محاولة تعديل تسليم معتمد ومغلق | العبث بمخرجات تم تقييمها سابقاً | التحقق من شرط `milestone->status !== 'approved'` قبل قبول أي تسليم جديد. |
| **الوقت والتاريخ (Time)** | تسليم بعد انتهاء الموعد النهائي (Deadline) | خلاف بين الطالب والمشرف حول وقت التسليم | يقبل النظام التسليم ولكن يُسجل كـ `Late Submission` مع تنبيه المشرف. |
| **الوقت والتاريخ (Time)** | إنشاء مرحلة بتاريخ ماضي | اضطراب الجدولة الزمنية | تطبيق قاعدة التحقق `date\|after_or_equal:today` عند إضافة أي موعد مرحلة جديدة. |
| **الشبكة والنظام (System)** | الضغط المتكرر السريع على زر التسليم (Double Click) | إنشاء تسليمين متطابقين في نفس اللحظة (Race Condition) | تعطيل الزر برمجياً عبر الـ JS فور الضغط لمنع التكرار. |
| **الشبكة والنظام (System)** | حفظ غير مكتمل أثناء تقييم المشرف | عدم اتساق بين رصد الدرجة وحالة المرحلة | استخدام `DB::transaction` لضمان إتمام كافة عمليات الحفظ كعملية ذرية واحدة. |

## 9. خطة الاختبار وضمان الجودة (Quality Assurance & Testing)

1. **Feature Testing:**
   * اختبار مسار تسجيل الدخول وإنشاء الحسابات الجديدة (`AuthTest`).
   * اختبار حماية الصلاحيات ورفض غير المصرح لهم (`EdgeCasesValidationTest`).
   * اختبار عمليات رفع التسليم وتقييم المشرف وحساب النسب (`SubmissionAndReviewWorkflowTest`).
   * اختبار إنشاء المشاريع والمراحل من قِبل المشرفين (`ProjectAndMilestoneTest`).
2. **التكامل المستمر (CI/CD):** تشغيل كافة الاختبارات الـ 19 تلقائياً عبر GitHub Actions قبل السماح بدمج أي فرع في `main`.
